# iCloud / ICAPI 固定取码策略

## 范围

仅 `generic_api` 来源且取码地址为 `https://icapi.oaibx.com/api` 的记录使用此策略。其他 API 来源的邮件基线与时效校验保持原规则。

本次只读核对最新 1000 个 iCloud 邮箱：均属于 `generic_api`，均使用 ICAPI，无需重新导入或修改素材/Token。

## 注册行为

1. 授权重定向到邮箱验证页。若服务端初始路由会话明确标记 `passwordless_email_otp_send_pending=true`，且邮箱/会话/模式匹配，执行一次页面初始化的 `POST /passwordless/send-otp`；这不是重发。其他状态不额外发码，不调用旧 `/email-otp/send` 或 `/email-otp/resend`。
2. 页面加载完成（若有待首次发送，则以该请求确认完成为准）后记时间，等待至该时间后的30秒，再请求素材中原始 API 地址。
3. 不建立基线，不加60秒延时，不做 settle，不用 `code_time` 筛掉接口已经给出的码。
4. 只接受外层 `code=1` 且 `data.code` 是六位数字；保留前导零，直接交给当前会话验证。
5. 本次取码失败或没有有效码，再等待30秒后请求；最多三次 GET，不走隐藏的代理回退或额外详情请求。
6. 三次都未取得码，错误精确为 `验证码未获取`。协议注册外层不会再把这三次放大成九次，也不会因取码失败自动重发邮件。
7. HTTP 401/403/429 立即停止，不自动重放；停止/暂停信号可在等待期间生效。日志不输出 Token 地址、响应正文或验证码。

这是用户明确选择的接口直读策略，不等于通过邮件 ID/时间戳证明了验证码属于本轮发信。服务端校验失败仍停止当前任务，不伪造成功。

## 人工流量补充核对（2026-10-30）

用户提供的人工成功登录流量显示：10:50:41 进入验证页，服务端路由会话标记待首次发送；10:50:53 页面初始化调用 `POST /api/accounts/passwordless/send-otp` 返回200；10:51:58 验证码验证返回200并进入回调。该样本是既有账号的 passwordless_login，不是新账号注册成功证据。

纯 HTTP GET 不执行页面的客户端 loader。仅凭验证页 URL 判断“已经发码”不成立；是否带 `auth_page` 查询参数也不是判断依据。协议流程保留完整落点，不删除查询参数，只按明确的会话状态补齐一次正常首次发码，包括页面要求的本会话 `authorize_continue` 初始化。使用现有 SDK 调用约定，不复用人工流量的凭据，不修改挑战实现。发码拒绝、限流或不确定响应立即停止，不自动重放或换路。

ICAPI 日志只记录 HTTP 状态、业务状态0/1/other和验证码字段是否为空/无效，不记录接口 Token、响应正文、验证码或登录态。离线测试使用合成夹具，不复制用户流量中的凭据。

首次发码的空 POST 必须显式保留 `Content-Type: application/json`：否则 libcurl 默认附加表单类型，实测返回400 `unsupported_content_type`。已用真实 curl_cffi + 本机 HTTP 夹具验证空请求体与 JSON 请求头。
