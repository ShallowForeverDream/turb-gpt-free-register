# 通用 API 邮箱：发码前快照与候选码筛选

协议注册在每次显式发码前读取对应邮箱的取码接口，并保存一次基线。读不到基线时不继续发码。发码后，**对于只有验证码数值的来源**，先等到发码时间满 60 秒，再开始读取；带邮件收件时间或邮件 ID 的来源仍按原来的元数据规则筛选。

## 数值差分规则

- 基线只接受有效的邮箱响应；`code` 和 `all_codes` 组合会构成已观察到的旧码集合。明确返回空列表表示已知为空；超时、HTTP 错误、无识别字段不当作空列表。
- 基线绑定邮箱和取码地址，必须来自发码之前且相距不超过 30 秒；不同邮箱或不同取码地址不能共用。
- 发码满 60 秒后，取码接口返回的当前候选码若不在基线旧码集合中，记作 `new_code_since_snapshot`。旧码继续等待，不提交。若顶层 `code` 未变化、`all_codes` 中恰有一个新增值，改用那个唯一候选；有多个新增值但顶层仍是旧码时继续等待，不盲猜最新。接口若提供 `all_codes`，所选候选必须确实出现在该列表里。
- 有可靠收件时间或邮件 ID 时优先按原有规则筛选；收件人不符、历史邮件、ID 不变、响应自相矛盾和已被拒绝的候选仍不返回。
- 集合只在内存保存密钥化哈希，不在日志或调试输出中打印原始验证码、凭据或完整取码地址。
- 注册器以发码调用完成时刻作为 60 秒等待的锚点，并将延时仅传给保存了数值快照的通用 API 来源；IMAP、Outlook 及手动收码流程不因此延迟。单轮原有最长等待时间包含这 60 秒。

## 证据边界

数值差分说明“这次读取看到了发码前快照里没有的数值”，**不等于证明这封邮件属于当前发码请求**。接口快照漏页、前一次请求的邮件晚到、接口混入其他邮箱、缓存未刷新、重复的六位数或短时间多封邮件，都可能造成误选、漏选或歧义。60 秒只是用户指定的等待参数，不是从真实邮件到达时间统计出来的阈值。

本次代码更新按这个候选规则运行，不把差分日志写成“已证明本次新邮件”。数值快照来源的候选若被服务器明确拒绝，只在**同一轮**等待最多另外两个不同候选；拒绝过的值不会再提交，也不会因此自动重发。三次用尽或等待超时则停止并提示核验。其他邮箱来源保持原有拒绝即停止语义；不会把任何拒绝都归因为多次发码，也不会绕过访问拒绝。

## 验证范围

`tests/test_registration_snapshot_delta.py` 使用虚构邮箱、虚拟时钟和模拟 HTTP 响应，覆盖注册入口传递快照、发码顺序、60 秒前不读、旧码排除、新候选读取、错误响应与来源隔离。`tests/test_otp_freshness.py`、`tests/test_otp_audit_guards.py` 和其他邮箱适配测试覆盖负控。旧任务日志和状态不会被重写；离线通过不代表已完成真实邮件或真实注册验收。
