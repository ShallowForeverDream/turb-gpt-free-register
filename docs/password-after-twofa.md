# 注册日志与 2FA 后补设 GPT 密码

## 日志显示

批次数量仍保存为任务计划，以保留原批次的剩余总数、邮箱预留和暂停/继续语义；未启动计划不进入日志列表。只有执行线程把任务原子切换为 running 并写入 started_at 后，才出现在日志页。

分页、筛选、数量和状态统计在 SQL 中统一排除未启动的批次计划，非分页接口也使用同一规则，不会出现先分页再隐藏造成的空页。暂停不影响在途账号；停止后未启动的计划不会变成一批空日志。旧版独立任务记录保持兼容。

## 密码顺序与保护

当前协议流程：注册并保存登录态 → 按原配置完成 2FA → 仅补设缺失的 GPT 密码 → 复核登录态。补设工作留在注册线程和注册并发名额内，不另排一个串行密码队列。

- 已保存 GPT 密码：直接跳过，不生成或覆盖密码。
- 未保存密码：先读取官网 add_password/eligibility。若官网确认已有密码，只记录跳过，不重置未知的旧密码。
- 仅在 2FA 明确成功且有已激活 TOTP、可用登录态时进入补设。2FA 失败、停用或无登录态时不提交密码。
- 使用官网设置入口的 post_login_add_password 重认证参数；按返回页面完成邮箱 OTP / 已有 TOTP 验证。仅匹配同一邮箱、明确添加密码标志的页面可以提交 password/add，不调用 password/reset。
- 邮箱沿用原来源与取码策略；ICAPI 等待 30 秒、SMSBower 签名 API 复用 30 秒/最多三次的读码与判错预算，不额外重发。
- 密码由安全随机生成器产生，官网明确确认成功后才保存到 extra.registration_password。邮箱密码、TOTP 和其他账号资料不被替换；密码只通过原有按需查看/导出功能读取，不写进日志。
- 提交后的超时或不明确响应记为未确认，私下保留候选但不把它导出为已设置密码，不自动重复提交。账号与 2FA 保留，任务标记部分完成供人工核验。
- 浏览器驱动目前不支持这个新增补设步骤，会明确报未完成，不暗中改用协议驱动。不会对历史账号执行批量改密。

官网说明：[在设置中添加或更新密码](https://help.openai.com/en/articles/4936828-resetting-or-changing-your-chatgpt-password)。接口契约来自用户提供流量中的官方前端，以及该流量 manifest 指向的官方静态密码页面资源；这些契约不是本次真实改密成功的证明。

可视化日志仍分注册、2FA、Codex 三部分，补设密码显示在第二部分；原始日志可单独筛选“GPT 密码”。

## 2026-11-01 密码失败日志复核与修复

现存密码记录来自 2026-10-31：6 个 `failed`、24 个 `uncertain`，没有已确认保存的密码。失败不是同一种原因：部分 ICAPI 请求失败后耗尽三次读取，另有 TLS/连接异常；24 个未确认记录已进入密码提交阶段。旧代码吞掉了异常消息和 HTTP 详情，因此不能从旧日志还原这些提交的确切响应，也不能认定 24 个密码都没有设置成功。

已核对用户提供流量中的官方 manifest，以及其引用的公开静态资源：

- [密码表单路由](https://auth-cdn.oaistatic.com/assets/route-CCx3vrjL.js) 在添加模式下提交 `/api/accounts/password/add`。
- [continuation 客户端](https://auth-cdn.oaistatic.com/assets/client-auth-session-BQUmFDD0.js) 以成功 HTTP 响应中的 `continue_url` 继续，不要求 `success=true` 或必须返回 `page.type`。
- [成功页面](https://auth-cdn.oaistatic.com/assets/route-CpOepDLd.js) 对应 `/reset-password/success`，显示密码已更改并引导正常登录。

旧测试只覆盖带 `success` 或成功 `page.type` 的响应，遗漏了只含正常 `continue_url` 的契约。新用例在旧实现下失败，修复后通过。这证明存在响应判定缺陷，不证明旧日志的全部失败都由此导致。

本次处理：

1. 同时识别无错误、成功状态码且跳转到同一 Auth 源 `/reset-password/success` 的响应；错误域名、非成功路径、要求再次 POST 或矛盾状态都不能确认密码成功。
2. 逐阶段记录操作与 HTTP 状态；失败保存脱敏错误码、信息和请求 ID。不记录密码、TOTP、Token、邮箱取码地址或原始响应正文。
3. 明确结构化 4xx 拒绝与超时/未知结果分开。只有明确拒绝才清除本次未应用候选；超时、非结构化错误和未知成功响应仍保留私有候选，且不自动再次提交。
4. 密码被确认保存后，Session 刷新异常不再改变密码成功事实。设置密码可能影响现有登录态，仍须独立完成收尾 Token 复核；不能把旧 AT 失效当成账号停用或再次设置密码的理由。
5. 新旧账号表格分别显示“设置失败”“设置未确认”“设置中”“已有密码（未留存）”，不再将所有未保存密码的状态都显示成“未设置（OTP登录）”。
6. ICAPI 失败日志区分请求异常类型与 JSON 无效，仍保留 30 秒/最多三次、不重发、不自动切换路线的原规则。

离线回归：Python 876/876、Node 91/91 通过。历史账号和候选密码没有被批量修改、标记成功或重提；没有真实改密实测。历史未确认结果需通过正常登录核验，不能由修复后的代码倒推为已成功。

队列空闲后已备份并重启网页服务，新旧页面均 HTTP 200 且已加载密码状态控件。部署前后 7 张业务表的内容摘要及 `.env` 哈希保持一致，历史状态仍为 6 个失败、24 个未确认。
