## 当前实现

配置中启用 `USE_EMAIL_SERVICE=True`，注册页选“只用 SMSBower Gmail”，或设置 `EMAIL_SOURCE=smsbower_mail`。
Key 优先使用 `SMSBOWER_MAIL_API_KEY`，留空复用 `SMSBOWER_API_KEY`。本次修复没有改动真实 `.env`、启动服务或提交真实注册任务。

1. 协议驱动先完成不依赖邮箱的网络预检和 CSRF，再领取付费邮箱。浏览器驱动继续等找到邮箱输入框才领取。
2. 先检查地址、服务、域名、别名、等待时间和 Key；错误配置不会先买邮箱。
3. 领取和状态操作发送前，先把意图写入项目 SQLite 的 `mail_activations` 表。网络中断、HTTP 拒绝、损坏响应不会自动重放购买/状态写入；未知购买结果会阻止同一供应商凭据再次自动购买。
4. 收码使用 `mailId`，状态操作使用 `id`。明确无库存才有界等待；余额不足、业务错误、403/429、非 JSON 立即结束当前操作。
5. 同一任务保留同一激活；进程内锁串行化该激活操作，数据库事务保护状态写入意图。重复邮箱/原始 Gmail/激活 ID 不覆盖已有任务绑定。
6. OTP 必须是六位字符串，保留前导零；已用码摘要和排除码阻止重复返回。摘要先保存，再确认 `setStatus=5`，成功后才把码交给注册流程。
7. 完整注册及已启用的后处理成功才 `setStatus=3`；未创建而放弃才 `setStatus=2`。创建已确认但后续失败时保留激活，不让队列的第二次清理误取消。
8. 换绑后的查活可能还需要邮件 OTP，因此不会在查活前关闭激活；原会话查活成功才关闭，转入后台查活时保留。
9. 关闭状态和结果不确定的状态跨重启保留；关闭后收码明确失败，不恢复成可用激活、不自动购买新邮箱。旧版 `extra_json` 缺少生命周期字段时要求核对平台，而不是猜测仍有效。
10. `failed_created` 只对激活型来源有特殊含义，其他邮箱池仍映射为原有 `failed`，不会改变旧来源状态契约。

## 保留的限制

- 供应商这条链路不提供邮件时间戳，`after_ts` 不能证明邮件属于某一轮请求；已用码去重不等于时间戳验证。
- 临时激活关闭不代表拥有 Gmail 密码/OAuth 或永久收件能力。日后重新登录所需邮件验证，需要仍有效的合法邮箱访问渠道。
- 对结果不确定的购买/状态操作，必须先在供应商后台核对真实订单。数据库里的待核对状态不能自动当作退款、取消或成功扣款。
- 运行配置变更后，旧激活仍绑定原 API 地址/Key 指纹；换 Key 不会静默把旧 mailId 发给另一个账号。
- 单次 HTTP 超时受剩余等待预算限制；底层 requests 的连接/读超时不等于可强制中断任意慢速响应的硬实时截止。

## 自动发码分支修正

用户提供的运行日志显示授权重定向已落到 `https://auth.openai.com/email-verification`，并确认页面加载即发送验证码。该分支现在直接等待原会话的邮件，不再额外调用 `GET /email-otp/send`，也不点击重发。

- 邮件快照和 `after_ts` 在授权导航前记录；不能在页面加载结束后重设时间下界或抓取基线，否则可能把本轮快速到达的邮件当作旧邮件。
- 如果落到 `create-account/password`，仍提交密码并跟随服务端返回的发码地址，采用这次密码提交前的新快照和时间下界。不能把这个新状态所需的发码与重复首次发码混为一谈。
- 参考包 `auth_flow.py` 的 passwordless 分支说明授权继续步骤可能已经发码；它也有按邮箱池默认主动 resend 的策略。本项目没有照搬该默认重发策略。
- 原有超时后有界重发与首次进入验证页分开；本次没有改动查活、2FA 等其他认证流程的首次发码契约。
- 浏览器驱动首次进入验证码页本来就不是靠额外 `send_email_otp` 触发，本次重点修正的是日志中的协议注册入口。

此分支修正后的相关离线回归共 271 项通过，覆盖直接等待原验证码、导航前快照/时间基准、密码分支独立发码、已有账号与注册后处理；没有执行真实发码或注册，也没有重启现有服务。
