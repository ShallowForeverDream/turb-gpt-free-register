# SMSBower Gmail 签名 API 直读取码

## 问题

原任务569是 `generic_api` 邮箱素材，接口为 `https://smsbower.page/api/mail/getCodeBySignature`，不是 SMSBower 手机短信购号，也不是自动购买临时邮箱的 `smsbower_mail` 来源。原日志显示首次发码成功，但通用快照逻辑因 `unchanged_code_set` 始终没有提交验证码。

## 修改

- 注册和2FA授权、页面初始化、验证码验证、保存与收尾流程不替换，仅为该邮箱接口增加独立取码适配。
- 只匹配 HTTPS、精确域名/路径、标准端口、无 URL 用户认证信息、恰好一个非空 `s` 参数。其他 API 来源保留原有规则。
- 发码确认/页面就绪后等30秒，GET 原始素材地址；只接受外层 `status=1` 与顶层六位数字 `code`，保留前导零。忽略 `all_codes`，不建立基线、不做时间戳/集合差分、不加60秒等待或 settle，不改签名 URL，不调用重发接口。
- 本轮没有验证码或网络/JSON错误，再等30秒读取；明确的验证码判错也从判错时起等30秒，再读取 `code`。读取和验证码判错共用同一状态计数，总共最多三次 API GET，验证提交不会另开三次读取循环。注册与2FA分别持有独立的挑战预算。
- 三次未获取时报“验证码未获取”；第三次得到的验证码仍判错，报验证失败并停止。访问拒绝、限流、无效认证会话不当作验证码判错自动重试；不换路、换号或改注册状态冒充成功。
- API签名、响应正文、历史码与实际验证码不写入新增日志。可视化日志也能识别该接口正在接码。

这是用户明确选择的直接读取策略，不证明 API 返回的历史/缓存验证码属于本次发信，最终以当前认证会话的验证响应为准。

## 验证

合成夹具和假时钟覆盖：精确接口匹配、无基线 HTTP、原始地址、顶层 `code`、前导零、忽略 `all_codes`、30秒锚点、空码/JSON/网络故障、三次上限、验证判错后等待、注册与2FA共享预算、错误会话不重试、日志脱敏。没有使用用户提供的签名或真实验证码作为测试常量。

原任务569的历史错误和日志保留。用户要求的单邮箱实测通过既有“指定邮箱注册”入口提交，仅选原任务邮箱，不扩大批次；实际结果另附验收记录。
